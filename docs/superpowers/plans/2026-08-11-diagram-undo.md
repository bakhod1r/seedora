# Diagram Undo/Redo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the mapping editor undo and redo for plan edits, so a wrong drag or a mistaken generator change is one keystroke to reverse.

**Architecture:** Every plan edit already funnels through one function — `pushPlan()`, which PUTs the whole plan and applies the server's reply. That single commit point is the seam: keep a snapshot of the plan as of the last successful commit, and on the next commit push the old snapshot onto an undo stack. No call site has to remember to snapshot, and nothing can drift out of sync, because the stack is fed by the same function that talks to the server.

**Tech Stack:** Plain ES2022 in `internal/ui/assets/app.js` — no framework, no build step. Tests are `node --test` against the existing `tests/ui/` vm harness, plus one Playwright test in `tests/browser/`.

## Global Constraints

- **No build step, no dependencies.** `app.js` is a plain script served from a Go binary. Nothing may require bundling, transpiling, or a `package.json`.
- **Top-level function declarations.** The `tests/ui/` harness reads functions off the vm global; anything that needs testing must be declared with `function name(...)`, not `const name = () => ...`.
- **Go 1.26, `CGO_ENABLED=0`.** Unchanged by this work, but `make pages` must be re-run so `docs/` does not drift from `internal/ui/assets/`.
- **Scope is plan edits only.** Generators, uniqueness, references, cardinality, row counts, and column order. See "Deliberately out of scope" at the end — the exclusions are decisions, not omissions, and Task 5 documents them.
- **Verify before claiming done.** Every task ends with a command whose output is checked, not assumed.

  assert.equal(app.undoLabel(), `edit ${limit + 9}`);

  state.plan.tables.users.rows = 9999;

```javascript
// ---- undo
//
// Every plan edit commits through pushPlan, which is what makes undo cheap:
// there is one place that knows an edit has happened and succeeded, so there is
// one place to snapshot from. Individual edits do not have to remember to
// record themselves, and none of them can forget.
//
// What is stored is the whole plan rather than a diff. A plan for a large
// schema is a few hundred kilobytes and an edit touches one column of it, so a
// diff would be smaller — and it would also be a second representation of the
// plan to keep correct, for a saving nobody can perceive.

// UNDO_LIMIT bounds what the stack holds. Twenty-five edits is further back
// than anyone reaches by keystroke, and it stops a long session from keeping
// every plan it ever had.
const UNDO_LIMIT = 25;

const history = {
  past: [],   // [{label, plan}] — oldest first
  future: [], // [{label, plan}] — what undo took away
  // base is the plan as of the last successful commit. It is what gets pushed
  // onto past when the *next* edit commits, which is why an edit does not need
  // to snapshot before mutating.
  base: null,
};

function snapshotPlan() {
  return app.plan ? structuredClone(app.plan) : null;
}

// resetHistory starts over. Connecting to another database makes every stored
// plan meaningless — they describe tables this database may not have.
function resetHistory() {
  history.past = [];
  history.future = [];
  history.base = snapshotPlan();
}

// recordEdit pushes the plan as it was before the edit that just committed.
function recordEdit(label, before) {
  if (!before) return;
  history.past.push({ label, plan: before });
  if (history.past.length > UNDO_LIMIT) history.past.shift();
  // Editing after undoing abandons the branch that was undone. Keeping it would
  // mean a redo that reapplies a change on top of a plan it was never made
  // against.
  history.future = [];
}

function canUndo() { return history.past.length > 0; }
function canRedo() { return history.future.length > 0; }

function undoLabel() {
  return canUndo() ? history.past[history.past.length - 1].label : null;
}

function redoLabel() {
  return canRedo() ? history.future[history.future.length - 1].label : null;
}
```

Replace `pushPlan()` (line 292–298) with:

```javascript
// pushPlan sends the whole plan and applies the server's reply.
//
// A label makes the edit undoable and is what the toast and the button tooltip
// say. Saving without one — before a run, say — is not an edit and does not
// belong in the history.
async function pushPlan(label) {
  const before = history.base;
  try {
    applyState(await api("PUT", "/api/plan", app.plan));
  } catch (e) {
    toast(e.message, "bad");
    return;
  }
  // Recorded only after the server has taken it. An edit it refused never
  // happened, and offering to undo it would be offering to undo nothing.
  if (label) recordEdit(label, before);
  history.base = snapshotPlan();
  updateHistoryButtons();
}
```

Then add, immediately after it:

```javascript
// undo puts the plan back the way it was before the last recorded edit.
//
// It goes through the server like any other change, because the server holds
// the plan and a local revert would leave the two disagreeing until the next
// save. That also means an undo can fail, and a failed undo has to leave the
// stack exactly as it found it.
async function undo() {
  if (!canUndo()) return;
  const entry = history.past.pop();
  const current = history.base;

  app.plan = structuredClone(entry.plan);
  try {
    applyState(await api("PUT", "/api/plan", app.plan));
  } catch (e) {
    history.past.push(entry);
    app.plan = current;
    toast(e.message, "bad");
    return;
  }

  history.future.push({ label: entry.label, plan: current });
  history.base = snapshotPlan();
  renderDiagram();
  updateHistoryButtons();
  toast(`Undid ${entry.label}`, "good");
}

// redo reapplies what undo took away.
async function redo() {
  if (!canRedo()) return;
  const entry = history.future.pop();
  const current = history.base;

  app.plan = structuredClone(entry.plan);
  try {
    applyState(await api("PUT", "/api/plan", app.plan));
  } catch (e) {
    history.future.push(entry);
    app.plan = current;
    toast(e.message, "bad");
    return;
  }

  history.past.push({ label: entry.label, plan: current });
  history.base = snapshotPlan();
  renderDiagram();
  updateHistoryButtons();
  toast(`Redid ${entry.label}`, "good");
}
```

// updateHistoryButtons reflects the stack in the toolbar. Defined here because
// pushPlan calls it; the buttons themselves arrive with the bindings.
function updateHistoryButtons() {
  const undoBtn = $("btn-undo");
  const redoBtn = $("btn-redo");
  if (!undoBtn || !redoBtn) return;

  undoBtn.disabled = !canUndo();
  redoBtn.disabled = !canRedo();
  undoBtn.title = canUndo() ? `Undo ${undoLabel()}` : "Nothing to undo";
  redoBtn.title = canRedo() ? `Redo ${redoLabel()}` : "Nothing to redo";
}

## Deliberately out of scope

Each of these is a decision with a reason, not something forgotten. Task 5 writes them down where a user will find them.

- **Schema changes.** Creating, dropping, and altering tables is reviewed as SQL and applied in a transaction. The moment to change your mind is the review dialog. Undoing an applied `DROP TABLE` would mean this tool inventing a table it never saw the contents of, and on MySQL the transaction it would need has already committed.
- **Layout.** Dragging a card is already reversible by dragging it back, and **Tidy up** recomputes the whole arrangement from the foreign keys. Putting it in the same stack as plan edits would also mean a single Cmd-Z sometimes moving a card and sometimes changing data, which is the kind of ambiguity undo exists to avoid.
- **A seeding run.** Rows written to a database are the database's, and a run that has committed is not this tool's to reverse. The confirmation before a truncate is where that decision is made.

## Plans to follow

The other diagram work, each independently useful and each its own plan, in the order they are worth doing:

1. **PNG and SVG export.** The edges are already SVG and the cards are already positioned; this is serialising what is on screen. The diagram is the thing people paste into a pull request.
2. **Namespace grouping.** `model.Table.Schema` is populated and the Postgres driver reads every non-system namespace, but the diagram draws them as one undifferentiated set. Anyone with more than `public` sees a schema that is not the shape of their database.
3. **Run heatmap.** `app.lastRun.byTable` already holds what each table got and the card already shows it; colouring the diagram by it makes a finished run readable at a glance.
4. **Minimap.** Twenty-three tables already exceed a screen at a readable zoom.
5. **Card notes.** Nowhere to write "this one is legacy" or "never seed this".
6. **Schema comparison.** `ddl.Missing` already computes the difference between the repository's migrations and the live database, and the diagram already draws the missing tables as drafts. Showing changed and removed with the same clarity is a small step from there.
